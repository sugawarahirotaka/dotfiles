# 技術説明の組み立て方

このリファレンスは、主規範に加えて、機構、原因、数式、概念比較を説明するときに使う。

## 答えから機構へ進む

短い技術説明は、次の順で進める。

1. 問いへの答えを一文で述べる。
2. 答えが成り立つ機構または理由を示す。
3. 証拠、具体例、式、比較で確かめる。
4. 成り立たない条件または誤解しやすい境界を示す。

背景史、用語一覧、調査手順から始めない。
読み手が答えを理解するために必要になった位置で補う。

## 原因を経路として説明する

原因候補ごとに「何を変え、どの中間量を通じ、何へ効くか」を示す。
直接検証した経路と、観測に整合するだけの経路を分ける。

> pseudo観測はposterior meanを変える。
> meanの変化がstandardized improvementを上へ動かし、`Φ(z)`による減衰を弱める。
> その結果、元から存在した空間勾配がEI optimizerへ伝わりやすくなる。

三段階以上の依存関係に分岐や合流がある場合は、短い番号付きの流れまたはMermaid図を検討する。
単純な一方向の関係は文章で書く。

## 数式を説明する

式を出す前に、何を判定するための式かを一文で示す。
式の後には、各項の定義を繰り返すのではなく、結論に効く項を説明する。

- 記号は使う直前に定義する。
- 同じ対象へ複数の記号や呼び名を与えない。
- 途中式は、読者が帰結を検証するために必要なものだけ残す。
- 等式、近似、上界、経験的な関係を同じ強さで扱わない。
- 式の直後に、増減、極限、依存関係など、読み取るべき意味を書く。
- 式が文章の主張を精密にしない場合は追加しない。

## 比較軸を固定する

二つ以上の手法や概念を比べるときは、比較軸を先に固定する。
各対象について別々の紹介文を書き、読み手に対応関係を探させない。

比較軸が一つなら文章で書く。
複数の対象を複数の軸で比較する場合は、小さな表を使う。

|観点|raw EI|LogEI|
|---|---|---|
|最適化対象|EIそのもの|EIの対数表現|
|tailでの数値安定性|勾配が表現限界へ近づきやすい|小さい値の相対差を保ちやすい|
|変えるもの|獲得関数の数値表現|獲得関数の数値表現|

表の後では、判断に効く差を文章で述べる。

> LogEIはposteriorを変えず、同じ獲得基準を数値的に扱いやすい形で最適化する。
> したがって、posterior geometryを変えるPolyBOとは介入箇所が異なる。

## 箇条書きへ逃げない

主張、理由、例外の関係は段落でつなぐ。

悪い例：

> - **性能**：後半で改善した。
> - **原因**：tail attenuationである。
> - **制約**：F21では改善しなかった。

改善例：

> 後半の性能改善は、tail attenuationの緩和と同じ時期に現れた。
> ただし、F21ではtailも性能も改善していないため、この機構は有力な説明ではあるが、全関数に共通する説明ではない。

箇条書きは、独立した条件や手順を走査するときだけ残す。

## 詳細度を制御する

- 読み手がすでに知る前提を繰り返さない。
- 後で参照しない固有名、ファイル名、時刻、ログ断片を本文へ出さない。
- 具体例は、抽象説明で残る誤解を一つ解くために使う。似た例を重ねない。
- 主要な問いに答えない調査経緯は、求められた場合だけ「確認内容」として分ける。
- 正確さに必要な限定は残すが、全ての例外を同じ段落へ詰め込まない。

読み手が次に尋ねるはずの問いが本文から答えられるか確認する。
ただし、先回りしすぎて回答を小さな教科書にしない。
